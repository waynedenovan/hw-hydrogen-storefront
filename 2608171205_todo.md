## RESOLUTION (2026-08-17) — COMPLETE, VERIFIED LIVE

Both feature confirmed already fully built end-to-end (custom.images /
custom.tech_info_pdf metafields, app/lib/supplierImages.ts, "Technical

was a DATA-GENERATION problem in hw-storefront-ui-node-docker, not a missing
feature. No hw-hydrogen-storefront-node-docker code changes were needed.

### Root cause

`scripts/generate-agrinet-media.mjs` only matched a product's image/tech-doc
by an EXACT normalized productId (`normalizeProductIdForImage`: strips only
" "/"/"). Two real, distinct data-source formatting gaps meant this missed a
lot of otherwise-real data:

1. Images: 1,809/13,922 products had zero image via the strict rule. Most had
   a `-` in their productId (e.g. `240015-008`) that the real image library
   files don't have (`240015008.jpg`) — a deliberate prior decision not to
   loosen the primary rule (session 2607240845), so these files sat unused.
2. Tech docs: **0/13,922** products had ANY tech doc — Agrinet's own supplier
   feed never actually populates `enrichedData.tech_info_pdf` (the field the
   pipeline was reading), so the feature had zero real data despite being
   fully built.

### Fix

Extended `generate-agrinet-media.mjs` with THREE gap-fill tiers — used ONLY
when the primary rule-based matching finds nothing for a product, per Wayne's
explicit instruction not to change the primary/strict matching behavior:

1. `images_confirmed.md` (16,735 manually-reconciled SKU→filename rows) —
   0 usable matches (would have needed the same dash-loosening as #2, so
   nothing new beyond what #2 already covers for this catalog).
2. Dash-strip (`normalizeProductIdForImageDash`: also strips `-`) reapplied
   against the SAME primary image-library index and, separately, against
   `tech.md`'s SKU column (tech.md's SKUs are already dash-free; many real
   productIds aren't — same underlying gap, opposite side). Collision-guarded
   for images (a pre-pass computes every file the strict rule already
   assigned to ANY product; a gap-fill is only applied if it doesn't try to
   steal one) — caught and correctly skipped 2 real cases (`319-100`,
   `319-110` would have stolen `319100`/`319110`'s own photos). No collision
   risk found for tech docs (multiple products legitimately sharing one PDF
   is normal, not a bug; verified zero ambiguous productId collisions).
3. `tech.md`'s referenced PDF filename resolved against the real PDF library
   (`/home/rogue/coding/hw/TECHNICAL SHEETS MAGENTO_Updated 13 May 2026.../`,
   1,286 files — not previously wired into either repo) via exact match, then
   a single-unambiguous-candidate token-containment match (2+ candidates or
   0 candidates → reported, never guessed).

Results: 345 products gained a real image (417 files copied), 375 gained a
real tech doc (126 distinct PDFs copied) — both via `--copy` into
`hw-hydrogen-storefront/media/suppliers/agri/`(`/docs/`), which both repos'
docker-compose bind-mount, so no container rebuild was needed for the files
themselves. Every gap-fill decision (matched, ambiguous, no-candidate,
collision) is written to a new `{ts}-gapfill-report.md` alongside the
generated `{ts}-media.json`, matching this codebase's existing
`img_not_matched.md`/`prodid_not_matched.md` "surface the gap, don't guess"
convention.

`/home/rogue/coding/hw/agrinet/other/missing_images.md` (1,464 remaining
gapless products + best-effort unused-file suggestions for manual review) and
`missing_images.01.md` (14 short-shared-prefix-code families, e.g.
`AO762/0134`, excluded from the main file because the prefix alone can't

### Reusable pattern (logged to MCP-Bridge)

Gap-fill-only overlay on an existing exact-match rule: when a matching rule
is deliberately strict (won't loosen a productId normalization because a
looser rule would introduce false positives elsewhere), a supplementary data
source can still be used SAFELY as a gap-filler — apply the SAME strict rule
to the supplementary source too (no new normalization invented), only for
records the primary rule found nothing for, and collision-guard any tier that
assigns an exclusive resource (one image "belongs" to one product) against
everything the primary rule + earlier gap-fill tiers already claimed. A
non-exclusive resource (many products sharing one PDF) doesn't need the
collision guard — check which case you're in before assuming symmetric
tiers need symmetric guards.

### Investigation: the delete-guard race — inconclusive, likely NOT an app bug

Revisited the transient ENOENT 500 flagged earlier
(`suppliers/agrinet/price/260817133627-prices.json`, referenced but
apparently missing at read-time). Confirmed via full-repo grep that
`deleteAgrinetFile()` (`agrinet.server.js`) is the ONLY file-deletion code
path anywhere in this app (checked both repos' `app/`/`scripts/`, excluding
tests) — nothing else can delete an Agrinet file. Read `deleteAgrinetFile()`
closely: it re-reads the live directory at delete-time (not a stale snapshot)
before refusing to delete whatever is currently newest, so a single request
can't be tricked into deleting the file `findLatestFile()` is about to read.

While investigating, found the "missing" file had REAPPEARED — same exact
timestamp (mtime `Aug 17 15:49`) as when `generate-agrinet-media.mjs` and
`app.import.jsx` (flagged earlier this session as mysteriously reverted to
pre-session content) were ALSO found restored back to their correct,
session-edited state. All three unrelated files changing at the identical
instant is much better explained by ONE external event touching a broad
swath of the working tree (a backup/restore/sync tool, `git stash pop`, an
IDE local-history restore, etc.) than by an application bug — the app has no
code path that could explain either the revert or the file's
disappear-then-reappear. **Not conclusively identified — Wayne didn't
recognize doing this deliberately.** No fix applied (nothing in the app
needs fixing); flagged as an environment mystery, not a code defect, unless
it recurs.

configured-value choice (no-op), not a missing/broken wiring. No code change
made — Wayne confirmed this was for his own reference.
