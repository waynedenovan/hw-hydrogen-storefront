## Investigation (no bug here — confirmed architecture already supports independent per-tier colors)
All page backgrounds are driven by `app/styles/reset.css`, keyed off a page-type class (`home-page`, `product-page`, `account-page`, `contact-page`, `cart-page`, `collection-page`) computed in `app/components/PageLayout.tsx` (`isHomePage`/`isProductPage`/etc., lines 42-56) and applied both server-side to the `.page-bg` wrapper div (lines 124-136, correct on first paint) and client-side to `document.body` post-hydration (lines 58-111, used only for the overscroll-bounce canvas color).

Key finding, reusable: **Tier 2 and Tier 3 already share one selector.** `isCollectionPage` (`PageLayout.tsx:55-56`) matches any `/collections/...` path — both the main collection view (Tier 2, e.g. `/collections/power-products`) and the sub-collection view (Tier 3, e.g. `/collections/welding`) render with the identical `collection-page` class. So `.page-bg.collection-page` in reset.css already covers both tiers with one rule — no new class or architecture change was needed to let tiers differ; each tier already has its own independent CSS selector, this task just pointed three of them at the same value.

Text-contrast check (done before touching CSS, not assumed): all headings (h1-h5) get their own `rgba(50,50,50,0.85)` dark chip background from a blanket reset.css rule; other white-on-dark text (cart lines, menus, CollectionCard tile titles, product-detail `.page-card`) all sit on their own dark component backgrounds (`var(--menu-bg)` or per-component chips), never directly on `.page-bg`. So switching the page canvas from black/photo to light green does not break existing text contrast anywhere — confirmed live via screenshots below, no legibility regressions found.
