## Step 1b: Cookie usage audit

Full inventory of every cookie either repo sets, grepped for `Set-Cookie`,
`createCookie`, `createCookieSessionStorage`, `res.cookie`, `document.cookie`
across both repos' `app/`/`server.*`:

1. **`session`** (hw-hydrogen-storefront-node-docker, `app/lib/session.ts`,
   `createCookieSessionStorage`) — httpOnly, holds cart ID + OAuth state.
   Strictly necessary (login/cart/checkout functionality) — POPIA explicitly
   exempts this class of cookie from consent, only requires disclosure
   (covered by the Privacy Policy modal built in an earlier session).
2. **`cookie_consent`** (hw-hydrogen-storefront-node-docker, built session
   2607311150) — the consent record itself. Also exempt by the same logic
   every cookie-consent implementation uses: you cannot gate the mechanism
   that remembers "no" behind itself.
3. **Shopify's own storefront cookies** (`_shopify_y`, `_shopify_s`, plus
   Shopify's internal tracking-consent cookie) — set by Shopify's own
   Analytics/Customer Privacy scripts (loaded via `<Analytics.Provider>` /
   the Storefront API / checkout domain), not by this codebase directly.
   **Already gated** — session 2607311150 built
   `app/components/CustomerPrivacySync.tsx` which calls
   `useCustomerPrivacy().setTrackingConsent({marketing, analytics,
   preferences, sale_of_data})` from our own consent choice, the documented
   Shopify pattern for storefronts using a custom banner instead of
   Shopify's built-in one.
4. **`hw-storefront-ui-node-docker` (the admin app)**: grepped `app/`,
   `server.js` — **zero** cookie-setting code anywhere, including its public
   customer-facing PayFast redirect routes (`api.payment.initiate/notify/
   return/cancel.jsx`, hit by the customer's browser during checkout). Its
   own embedded-admin auth uses `@shopify/shopify-app-session-storage-prisma`
   (session-token/JWT based per Shopify's modern embedded-app model, not
   cookies) — confirmed via `package.json`, no cookie-parser/express-session
   dependency present. This app is fully out of scope for customer cookie
   consent: it never sets anything on a customer's device.
5. **Cloudflare Insights beacon** (`static.cloudflareinsights.com/beacon.min.js`)
   — observed in live console errors, auto-injected by Cloudflare's edge/proxy
   (a dashboard-level setting, not our code) and currently **fully blocked by
   this site's CSP for every visitor** regardless of consent (confirmed:
   `default-src` violation in console on every page load, both before and
   after consent). Flagging as informational only — since it's blocked for
   everyone unconditionally, this is over-compliant, not a gap. If Wayne ever
   wants Cloudflare Web Analytics working, that would need a CSP allowance
   *and* wiring it behind the Analytics category — not done, not asked for.
   No third-party GA/GTM/Meta Pixel/Hotjar-style script exists anywhere in
   either repo's source (re-confirmed via grep this session, matching last
   session's finding).

**Conclusion: no further implementation was needed.** Every cookie either
repo actually sets is accounted for and already respects the visitor's
choice (essential cookies exempt by design, Shopify's own cookies gated via
the Customer Privacy sync built last session). Step 1b's "implement any
needed changes" had nothing left to implement — last session's cookie
consent feature already closes this out completely.
